# 프로필과 인증: Tada 운영 기준

> 2026-10-21 기준 코드 검토 기록. 이 문서는 제품·구현 방향을 설명한다. Supabase 프로젝트의 실제 Auth 설정과 DB 마이그레이션 적용 상태는 별도로 확인해야 한다.

## 한눈에 보기

| 구분 | 무슨 역할인가 | 권장 기준 |
| --- | --- | --- |
| 계정 가입·로그인 | 사용자가 누구인지 확인하고 세션을 만든다 | 이메일 가입은 이메일 주소와 확인 절차를 기본으로 한다. Google 로그인은 별도 경로다. |
| 프로필 | 다른 사람에게 보여줄 이름·사진·지역 등 | 가입 방식과 분리해 여러 화면에서 같은 데이터와 표시 컴포넌트를 재사용한다. |
| 전화번호 인증 | 사용자가 해당 번호의 SMS를 받을 수 있는지 확인한다 | 가입·일반 이용에는 선택 사항. 번호가 실제로 필요한 기능에서만 요청한다. |
| 공개 범위 | 누가 전체 판매자 프로필을 볼 수 있는지 정한다 | 연락처 공개와 별도로 관리하고, 서버·DB에서도 접근을 제한한다. |
| 타다 충전 | 실제 거래 경험에 따른 평판 개념 | 이메일·전화번호·프로필 완성도와 혼동하지 않는다. |

## 사용자에게는 어떻게 보이나

1. 이메일로 가입하는 사용자는 이메일과 비밀번호를 입력하고 확인 메일을 받는다. 이메일 확인을 로그인 필수 조건으로 운영하려면 Supabase의 **Confirm Email** 설정도 켜져 있어야 한다. 코드의 안내 문구만으로 강제되지는 않는다.
2. Google 로그인 사용자는 별도의 OAuth 흐름을 거친다. 모든 가입 방법에 똑같은 ‘이메일 링크 클릭’ 화면을 강요하지 않는다.
3. 전화번호 없이도 프로필 작성, 탐색, 일반 활동을 할 수 있다. 프로필 설정의 전화번호는 ‘선택’으로 표기한다.
4. 번호를 입력하면 ‘미인증’ 상태로 둔다. SMS 코드를 확인하고 Supabase Auth가 해당 번호를 인증한 후에만 ‘인증됨’으로 표시한다.
5. 프로필 공개 범위와 연락처 공개 범위는 별도 설정이다. 전화번호를 인증했다고 자동으로 공개하지 않는다.

전화번호 인증은 **그 번호를 사용할 수 있다는 확인**이지, 신원 보증이나 추가 로그인 보안(MFA)을 뜻하지 않는다. MFA를 도입한다면 별도의 등록·챌린지·검증 절차로 설계한다. 서비스 등록의 업체 연락처나 예약 시 필요한 연락처 역시 계정 전화번호 인증 의무와는 별개로 판단한다.

## Supabase가 맡는 부분과 Tada가 맡는 부분

| Supabase Auth | Tada 앱·DB |
| --- | --- |
| 이메일·비밀번호/OAuth 로그인, 세션 관리 | 닉네임·사진·지역 등 프로필 편집과 표시 |
| 이메일 확인 시각, 인증된 전화번호/확인 시각 | 어떤 기능에서 추가 인증이 필요한지 결정 |
| 전화번호 변경 요청과 SMS 코드 검증 | 미인증 입력값과 인증된 번호를 구분해 안내 |
| 로그인된 사용자 ID 제공 | 프로필 소유권·공개 범위·거래 관계 접근 정책 |

이메일 확인 여부는 Auth 사용자 정보의 `email_confirmed_at`, 인증된 전화번호는 `phone`과 `phone_confirmed_at`을 기준으로 읽는다. `public.profiles.phone` 같은 일반 프로필 입력값만으로 ‘인증됨’을 판정해서는 안 된다. Auth의 `user_metadata`도 사용자가 변경할 수 있으므로 접근 권한의 근거로 사용하지 않는다.

현재 코드에서 [가입 함수](../../src/lib/auth.ts)는 이메일·비밀번호로 `signUp`하고, [가입 화면](../../src/components/auth/AuthForms.tsx)은 메일 확인을 안내한다. [프로필 페이지](../../src/app/market/dashboard/profile/page.tsx)는 Auth 확인 시각을 설정 폼에 전달한다. [프로필 설정 폼](../../src/components/dashboard/ProfileSettingsForm.tsx)은 `updateUser({ phone })`으로 변경 코드를 요청하고 `verifyOtp({ type: "phone_change" })`로 확인한다. 이 흐름은 Supabase의 전화번호 변경 방식과 일치하지만, 실제 SMS 발송에는 프로젝트의 전화 인증 및 SMS 제공자 설정이 필요하다.

### 현재 코드에서 정리할 점

- 설정 저장은 전화번호 입력값을 `public.profiles.phone`에 인증 전에 저장할 수 있다. **입력한 번호**, **Auth에 인증된 번호**, **외부 공개 여부**를 서로 다른 상태로 다뤄야 한다.
- 이메일 가입 화면은 확인 메일을 안내하지만, 실제 **Confirm Email** 설정은 저장소에서 확인되지 않았다. 운영 프로젝트 설정을 검증해야 한다.
- 새 [프로필 공개 범위 마이그레이션](../../supabase/migrations/20261021040719_profile_visibility.sql)은 저장소에 있다. 실제 DB 적용 여부와 공개/회원/거래 상대별 접근 테스트는 배포 환경에서 확인해야 한다.
- 전화번호 변경은 민감한 Auth 작업이다. 기존 번호의 미완료 변경 요청, SMS 발송 제한, 잘못된 코드, 번호 재사용 등의 실패 사례를 테스트한다.

## 재사용 가능한 프로필 구성

새로운 거대한 ‘프로필 컴포넌트’를 여러 페이지에 복사하지 않는다. 기존 [프로필 사진 컴포넌트](../../src/components/dashboard/ProfilePhotoUploader.tsx), [판매자 프로필 카드](../../src/components/market/SellerProfileCard.tsx), [설정 폼](../../src/components/dashboard/ProfileSettingsForm.tsx)을 출발점으로 다음 책임을 분리한다.

| 책임 | 쓰이는 곳 |
| --- | --- |
| 프로필 데이터 읽기·정규화 | 마이페이지, 설정, 판매자 페이지, 거래 화면 |
| 작은 프로필 표시 카드/아바타 | 목록, 메시지, 리뷰 등 |
| 전체 공개 프로필 표시 | 기존 판매자 프로필 페이지 |
| 프로필 편집 및 저장 | 프로필 설정 페이지 한 곳 |
| 이메일·전화 인증 상태 표시와 액션 | 설정 페이지, 필요한 단계의 안내 |

표시용 컴포넌트는 인증이나 저장을 직접 수행하지 않고 필요한 데이터와 상태를 props로 받는 편이 안전하다. 공개 화면에는 허용된 최소 정보만 전달하고, 개인 연락처를 통째로 전달하지 않는다. 프로필 공개 범위에 따라 전체 페이지 접근을 제한해도 상품·후기에 필요한 최소 판매자 정보는 별도 정책으로 유지한다.

## 구현·검증 순서

1. 운영 Supabase의 Confirm Email, OAuth, 전화 인증 및 SMS 제공자 설정을 확인한다.
2. 이메일 가입·확인·재로그인과 Google 가입을 각각 검증한다.
3. 전화번호를 비워둔 계정, 입력만 한 계정, SMS 인증한 계정을 구분해 UI와 데이터 원천을 정리한다.
4. 공통 프로필 데이터 모델과 표시 컴포넌트를 기존 구성요소에서 추출한다. DB 스키마 변경은 필요한 경우에만 별도 검토한다.
5. 공개 범위 마이그레이션 적용 상태와 익명/회원/확정 거래 상대 접근을 각각 검증한다.
6. 인증 상태를 타다 충전 수치와 섞지 않고, 모바일·데스크톱에서 같은 의미로 표시한다.
